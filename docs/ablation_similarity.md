# 消融：字符串相似度判据（复现 CN03 一类做法）

> 目的：把"读型 BOLA 判定 = 比较攻击者响应与属主响应的字符串相似度"这条常见
> 判据单独跑一遍，量化它在本基准上的误报。
> 复现：`make ablate-similarity` / `make ablate-similarity-novis`，再 `make ablate-report`。
> 日期：2026-11-03（L3 补齐后重跑；旧数据作废）

---

## 1. 实现口径

| 项 | 取法 |
|---|---|
| 参照响应 | 用**受害者自己的 token** 请求同一个 URL，取响应 body（JSON 优先，非 JSON 走 `textract`） |
| 参照时机 | **必须在 setup 状态仍有效时取**（软删除类实例的正文只在"已删除"状态下可见） |
| 相似度 | `difflib.SequenceMatcher`，JSON 排序键后比较，阈值默认 **0.90** |
| 判定 | 攻击者 2xx、参照响应 2xx、相似度 ≥ 阈值 → VULN |
| 写型 | 仍走副作用二次确认（只替换读型判据，保证差异只来自判据本身） |
| 可见性 | 单独开关：`--no-public-suppression` 模拟"没有公开资源模型"的检测器 |
| **空壳优待** | 单独开关：`--no-sim-empty-guard` 关掉"空响应不算泄露" |

实现：`pipeline/judge.py::judge_read_similarity`；入口：
`python -m pipeline.run --system crapi --judge similarity --tag sim_suppress`。
相似度是"越像越可疑"，不要求响应里出现归属证据或敏感字段——这正是它误报的根源。

## 2. 为什么有"空壳优待"这一列

这是本次重跑暴露出来的一个方法论问题，比数字本身更重要。

`_empty_shell`（"空响应不算泄露"）是**我们方法的一部分**：`no_owner_evidence`
对照之所以存在，就是因为它。如果在消融时把这条规则也送给相似度基线，
基线就白白拿到了结论的一部分，指标会系统性偏好我们的方法。

所以必须报两档：

- **给（`sim_suppress`，对基线最有利）**：先排除空壳再比相似度。这是**让步**，
  等于给基线我们能给的最大帮助。
- **不给（`sim_faithful`，忠实复现）**：CN03 一类做法没有"空"的概念，
  两个 `{"comments": []}` 的相似度就是 1.000。

**两档的差额就是"这条规则值多少钱"**：mock 上 0 → 33，crAPI 上 10 → 19。

## 2.1 相似度基线的第四个结构性缺陷：没有身份概念

这一条是修复"属主自读"缺陷后才暴露出来的，值得单列。相似度判据比较的是
**攻击者响应 vs 受害者响应**，它根本不知道"属主是谁"。于是：

- 攻击者恰好是属主时，两个响应**逐字节相同**，相似度 1.000 → 判越权。
- 这类用例按定义不是 BOLA 测试，评测层会跳过，**不进 precision 分母**；
  它们只出现在 `self_read_alerts` 这一披露列。

实测（`--judge similarity`）：

| 系统 | 配置 | 属主自读告警 / 属主自读用例 |
|---|---|---|
| MockShop | `sim_suppress` | **14 / 28** |
| MockShop | 归属证据（默认） | 0 / 28 |
| crAPI | `sim_suppress` | **16 / 22** |
| crAPI | `sim_faithful` | **22 / 22** |
| crAPI | 归属证据（默认） | 0 / 22 |
| VAmPI | `sim_suppress` | 0 / 0 |
| clean | `--owner-key-only`（复现历史实现） | **14 / 28** |

MockShop 的 14 条全部落在 `GET /api/orders/{id}`（8 条）与
`GET /api/users/{id}/orders`（6 条）——正是"响应逐字节等于自己"的两个端点；
crAPI 的 16 条落在 `GET /workshop/api/shop/orders/{id}`（10 条）与
`GET /workshop/api/mechanic/service_request/{id}`（6 条）。

**为什么这个数字重要**：它说明相似度基线的误报不是"阈值没调好"，而是
**判据形式本身不含身份信息**。给它再多的可见性声明、再好的阈值，都无法
区分"我读自己的订单"与"我读别人的订单"——两者的响应在它眼里完全一样。
这与 §VI-C1 的另外三个结构性来源（空容器、公开资源、未标注对象）是不同性质：
那三个可以靠外部信息（可见性模型、标注扩充）缓解，这一个只能靠**判据里加入
"这是谁的数据"** 才能解决，也就是 C3 的主张。

> 归属证据判据在同一批用例上 `self_read_alerts = 0`：它先问"响应里的身份是不是
> 攻击者本人的"（R0），再问"是不是受害者的"（R2）。这个顺序是必需的——
> 反过来先判归属，属主自读会因为 owner 值等于自己而命中。

## 4. 误报从哪来（三个机制）

### 4.1 空容器：`{"comments": []}` 的相似度是 1.000

crAPI 的 `/workshop/api/mechanic/service_request/{id}/comment` 对任意登录用户
都返回 `{"comments":[]}`；mock 的 `/api/users/{id}/orders` 对无订单的 uid 返回 `[]`。
两个空列表在字符串层面完全相同 → 相似度 1.000 → 安全实例被判成漏洞。

mock 上"不给优待"的 33 条 FP 里，**30 条来自 `/api/users/{id}/orders`**——
这正是为什么 mock 的 P 从 1.000 掉到 0.492。

即使**开着**可见性抑制也挡不住：这些端点不在 `public_paths` 里。
默认判据把空容器当作空壳（`_empty_shell`，含嵌套空容器）直接输出
`no_owner_evidence`；相似度判据没有"空"的概念。

> 这是最便宜、最可复现的一个反例：**结构相同 ≠ 数据泄露**。

### 4.2 公开资源：越像越是"漏洞"

社区帖子是公开内容，攻击者读到的和属主读到的一模一样，相似度必然 1.000。
关掉可见性模型后，crAPI 的 FP 从 10 增至 16（+6 条公开帖读/写），
VAmPI 多出 3 条资料页 FP。

相似度判据本身**没有任何机制**表达"这是公开的"。要么外挂一份可见性声明
（那就是我们的 `public_paths`），要么把这些全部计为漏洞。

### 4.3 未标注的第三方对象：像，但没有归属证据

crAPI 在"给空壳优待"配置下残留的 10 条 FP，**全部**落在未标注实例上：
内置用户 `test@example.com` / `admin@example.com` 的订单 4/5 与其维修请求 4/5。
任意登录用户都能读，按评测约定记为 FP。

严格说这些是**真 BOLA**，只是没标注。它暴露的是另一个问题：
相似度判据命中了也无法说明"这个对象属于谁"，所以既不能用于去重，
也不能用于生成可解释的报告；而证据判据在本基准上直接漏掉了它们
（身份集合里没有这两个内置账号），这是需要在正式标注里补的洞。
**注意这条偏差同时抬高我们的 FP 上限**，所以不是只对基线不利。

## 5. 结论（可直接写进论文）

1. 相似度判据在本基准上 **Recall 不掉**（所有 TP 的响应都与属主一致），
   代价全部体现在 **Precision**：crAPI 1.000 → 0.706（给优待）/ 0.558（忠实）。
2. 误报不是阈值问题：0.80 / 0.90 / 0.99 三个阈值结果完全相同。
3. 三类结构性误报——**空容器**、**公开资源**、**未标注第三方对象**——无法靠调阈值
   解决，只能靠"归属证据 + 可见性模型"。这直接支撑 C3 的设计选择。
4. mock 上"给优待"档零误报、VAmPI 全档零误报，而 crAPI 掉到 0.558：
   **只在一个靶场上评测会得出错误结论**，这正是 C1（多系统基准）的必要性。
5. **消融必须对基线忠实**。只报"给优待"那一档，等于把结论预先送给基线；
   那不是一个消融，是一次演示。

## 6. 局限

1. 参照响应由受害者 token 现场获取，要求评测者持有两个账号；这是本基准的
   设定，不是所有真实场景都满足。
2. JSON 排序键 + 20000 字符截断对相似度都是**有利**处理，因此这里的 FP 是**下界**。
3. 只替换了读型判据；写型仍用副作用确认。纯相似度工具在写型上会直接漏测，
   本实验没有把这一层算进去。
4. 只跑了 3 个系统、107 条标注，仍是链路验证，不是统计结论。
5. **L3 上的行为未单独统计**：相似度判据在软删除与查询型导出上的表现取决于
   参照响应是否取到，本次修复了参照时机（teardown 之前取），但没有按 L3 分层出表。
